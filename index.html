Abstract

Robot agents built on frontier vision-language models now solve most robot memory benchmarks. Does this mean they can remember what they need in a home, where people and machines keep moving things? Existing memory benchmarks cannot answer this question, because they pause the simulator while the model thinks: nothing can change during a decision, so whatever the robot remembers is still true when it acts. We introduce RoboLiveMem, a benchmark that runs the same memory tasks twice, once with the world paused while the model thinks and once with the world running. It contains 29 task families in three tiers, from 16 realistic BEHAVIOR-1K scenes of homes, workshops and a restaurant to controlled ManiSkill tasks. Every task mixes real changes with harmless look-alikes and runs without any change, so that no fixed strategy succeeds, and most tasks have a twin that keeps the change in view, which separates forgetting from acting too late. Testing 16 models on 34,176 episodes, we find three surprises. (1) Paused results hide the problem: when a remembered object changes in a realistic scene, the 8 frontier Claude and GPT models succeed in 97% of episodes on average with the world paused, but in only 50% with the world running, and their ranking changes: Claude Opus 5.5, which never fails when paused, succeeds in 44%. (2) Speed is not the fix: slower models do no worse, and models given only 2 s per decision still fall at least 36 points below their paused success. (3) Models see the change but act on camera frames from before it ended. Looking again just before acting closes most of the realistic gap, yet when identical objects are swapped several times, all nine models we test still lose points to memory.

01 · The protocol

Same task, same seed, two clocks: does the world wait?

A decision observes the world at time to, thinks for ℓ seconds and starts its command at tc = to + κ(ℓ). Under the paused clock κ = 0, as in existing benchmarks. Under the live clock κ = ℓ: while the robot holds still, people, robots and machines keep moving and the camera keeps recording, and those frames reach the model only with its next decision. A fixed clock κ = L varies latency on its own.

Phidden · paused

What current benchmarks report. A change can never fall between the frame a decision reads and the moment its command runs.

Lhidden · live

The world runs while the model thinks. A command decided on an earlier frame may act on a changed scene.

Vvisible twin · live

The same change at the same time, but a sticker, an open lid or a token keeps the decisive state in view.

SP − SL  =  (SP − SV)  +  (SV − SL)   live drop = execution (latency and acting on old frames) + memory

04 · Findings

Four questions, four answers

Q1 · Does paused success predict live success?

No. The ranking changes.

97%→50%

When a remembered object changes in a realistic scene, the eight Claude and GPT models fall from 97% on average with the world paused to 50% with it running. With no change, live success stays at 92 to 100%: the loss comes from changes that a paused world never lets happen.

Q2 · Is it latency?

No. A faster agent would not avoid the drop.

≥ 36 points below paused at 2 s per decision

The three slowest frontier models are the three most robust (Spearman ρ = +0.76 between latency and live success). Charged a fixed 2 s per decision, every model still stays 36 to 61 points below its paused success.

Q3 · Do agents see the change?

Yes, but they act on frames from before it ended.

62%→97%

On the realistic tier 51 to 80% of decisive decisions are stale, and on event seeds Opus succeeds in 1 of 34 stale and 21 of 23 fresh episodes. Looking once more before acting, the commit check, lifts Opus from 62% to 97% with no training.

Q4 · Is memory still a problem?

Yes, when identical objects are swapped again and again.

+1 to +22 points: the memory term, every model, every tier

Having to remember a change rather than see it costs every model points on every tier. On repeated swaps, looking again does not help: with the commit check, all nine models tested still lose at least 12 points to memory.

05 · Looking again before acting

One more look closes the realistic gap, not the swaps

The commit check: just before a command runs, the robot looks at its target once more; if the view there changed since the agent's last frame, the command is cancelled with a neutral message and the agent decides again. Live success on event and decoy seeds, without and with the check, and the visible twin with the check.

hidden, without the checkhidden, with the checkvisible twin, with the check

Realistic: the 13 scenes where the check applies (hidden n = 104, twins n = 56). Controlled: the three swap tasks (n = 80). Memory term: SV − SL with the check, on the families with a visible twin; what remains of it is memory that re-observation cannot replace.

07 · Code

Bring your model, your harness or your own agent

Every tier runs as an environment server with one protocol. The agent receives instructions, text and camera frames and answers with one command, and under the live clock the world keeps moving for as long as it thinks. The agent can be a bare model behind our reference harness, a model inside Claude Code, Codex or any MCP client, or your own system. The evaluation runs the paper's episodes and prints per-task and per-tier tables: paused, live, no change, the live drop and the memory term.

Results are reported as model + harness, with the latency source, because the harness changes both what the model sees and how long a decision takes. The simulators and their assets (BEHAVIOR-1K, MuJoCo, ManiSkill) are hosted by you; the repository holds the scenarios, servers and evaluation, plus a small 2-D tier that needs nothing.
